# ReturnLens：让服饰电商看清退货为什么发生

> 独立概念项目；使用模拟品牌、模拟数据和模拟 AI 输出，不代表真实客户上线成果。

## 1. 60 秒摘要

ReturnLens 是一个桌面端服饰电商退货分析 MVP。它把订单、退货、评价和客服聊天 CSV 在浏览器内读取，先做字段校验与文本脱敏，再用确定性规则按 SKU 聚合退货问题、计算直接损失与可挽回损失区间。操作者随后在问题详情查看脱敏证据、人工确认或修正归因，并把确认的问题推进到整改草案、整改看板和实验复盘。

这个项目验证的是一条可演示的决策闭环，而不是已经验证的商业成果：界面中的品牌、订单、AI 摘要、整改草案、趋势和实验结论均为概念演示数据；金额是排序用估算，不是审计结果。

## 2. 企业问题与目标角色

目标角色是需要决定“先改哪个商品或哪个页面”的服饰电商经营、商品运营和内容运营人员。退货原因通常分散在订单、售后原因、评价与客服对话中；只看金额难以判断先后，只看文本又难以把问题连接到 SKU、成本和可执行动作。

MVP 的目标是让操作者在一个流程中完成：导入数据、识别 SKU 问题、查看证据和置信度、人工复核、生成可编辑的整改草案，并将动作推进到验证。它没有接入真实店铺、客户账号或生产团队，因此不声称已改善退货率、节省成本或被任何客户采用。

## 3. 为什么普通 BI 和纯 AI 客服不够

普通 BI 可以汇总退货量或金额，却不必然保留每个 SKU 的脱敏文本证据、归因规则和人工复核入口。ReturnLens 用问题中心和详情页把这些信息放在同一条证据链上，并把可挽回损失明确显示为估算范围。

纯 AI 客服可能能生成措辞，但不能替代经营判断：它应当说明证据、允许驳回和改写、要求负责人/日期/指标后才能进入执行。本 MVP 用固定的“模拟生成”摘要和草案演示这一交互，不调用模型，也不将其输出当作事实或因果结论。

## 4. 产品闭环与信息架构

闭环是“数据与设置 → 经营总览 → 问题中心 → 证据复核 → 整改看板 → 实验复盘”。

- `/import`：加载内置模拟品牌或 CSV，显示字段映射、数据质量、本地脱敏提示、Token 价格假设和预算控制。
- `/`：按可挽回损失区间排序的经营总览与优先队列。
- `/issues`：问题筛选、问题状态和分析覆盖提示。
- `/issues/:issueId`：损失构成与估算、规则匹配、置信度、脱敏证据、人工复核和整改草案入口。
- `/actions`：已确认草案的待执行、执行中、待验证、已验证看板。
- `/experiments`：三种固定演示状态：有效、无显著变化、证据不足。

导入后，确定性分析立即创建派生问题；批次模拟则单独展示进度、预算和可结束的部分结果。这样，金额、证据、复核状态和动作状态不会被混为一个“AI 结论”。

## 5. AI 可信度、人机复核和成本控制

“置信度”不是模型置信度或因果概率。它由确定性公式计算：基础 45%，每笔退货加 5%，每条文本证据加 3%，文本证据累计贡献最高 +20%，总分最高 95%；页面同时解释它只表示证据充分程度。

归因使用退货原因与脱敏评价/聊天中的关键词匹配；确认、观察、修正和驳回均由人工触发。证据不足时，不能创建整改动作。摘要与整改草案均标有“模拟生成”，可编辑，草案在填完负责人、截止日期与目标指标前不能入看板；驳回原因会进入版本历史后再生成 V2。

预算面板按填写的每百万 Token 单价，在本地计算下一批的估算费用。超出上限前暂停，允许追加预算、切换备用价格假设或保留部分结果。这是界面层的模拟控制：MVP 不请求模型 API，也没有真实 Token、模型响应或账单。

## 6. 六个核心界面

1. 数据与设置：输入检查、映射建议、隐私提示、预算和分析进度。
2. 经营总览：可避免损失区间、高优先级问题、覆盖率和排序队列。
3. 问题中心：SKU、原因、渠道、置信度和状态筛选，以及部分结果覆盖提示。
4. 问题详情：脱敏证据、规则、金额区间、置信度说明和人工复核。
5. 整改看板：从草案到待执行、执行中、待验证、已验证的本地状态流转。
6. 实验复盘：固定样本展示有效、无显著变化、证据不足三种解释边界。

## 7. 失败、预算和部分结果

MVP 显式演示了三类不完整状态：预算上限会在下一批前暂停；“模拟模型超时”不会丢失已完成数量和已花费预算；操作者可确认结束并进入带覆盖率提示的问题中心。恢复页面后，派生任务状态、问题状态和整改动作会从浏览器 `localStorage` 重新读取。

这不是容错生产任务系统：没有真实队列、重试策略、幂等键、服务端断点、审计日志或跨设备恢复。所谓“部分结果”只是本地演示状态；它不证明真实模型在任意中断下都能安全恢复。

## 8. 技术取舍：真实规则与模拟 AI

真实、可重复的逻辑包括 CSV 解析、必填字段/数值校验、字段映射建议与需要确认的映射、正则脱敏、按 SKU 聚合、关键词归因、直接损失计算、置信度公式、15%–35% 可挽回损失区间、批次进度、预算预检和整改状态机。

模拟的内容包括内置品牌数据、AI 摘要、整改草案及其“重写”文本、经营趋势、实验样本、模型超时按钮和模型价格所代表的调用成本。模拟输出是代码中的固定夹具或确定性拼接，不是 LLM 生成；因此不应据此评价模型质量、成本、效果或泛化能力。

## 9. 验证结果与尚未验证的假设

已验证的是代码级行为：自动化测试覆盖导入校验、确定性分析、预算状态、问题复核、草案状态流转、部分结果提示、路由与实验状态；构建和 lint 可在本地执行。演示数据也可由脚本重复生成。

尚未验证的假设包括：真实商家是否认可问题排序、关键词归因对真实语言的准确性、脱敏规则的覆盖率、金额区间的财务有效性、草案是否带来可衡量改善、实验设计是否能分离因果、以及任何 ROI、节省金额、留存或采用率。页面中的实验“有效”等结论是固定模拟内容，不是产品研究结果。

## 10. 生产化扩展路径

生产化需要把浏览器内演示拆为受控服务：经批准的模型 API 与可追踪的 prompt/响应治理；身份认证、组织和角色权限；加密存储、数据保留策略和可审计脱敏；后端批处理队列、可重试/幂等任务与预算账本；以及订单、售后、客服、商品、实验和工单平台的授权集成。

同时应以真实财务口径校验损失计算，用人工标注数据评估归因，预注册实验口径并报告不确定性。以上是后续方案，不是当前 MVP 已实现的能力。
